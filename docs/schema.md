# itero schema

Reference for the data model in `internal/db/migrations`. Written before Epic 4
because the `conditions` document is parsed on the evaluation hot path, and a
shape that is only implied by the code that reads it is a shape that drifts.

## Model

```
projects
   |
   +-- environments ............ dev / staging / prod, keyed per project
   |        |
   +-- flags .................... the logical flag: key, type, metadata
            |                     one identity across every environment
            |
            +-- flag_environments  per-environment state: enabled, version
                     |
                     +-- variants ......... key -> JSONB value, one default
                     +-- targeting_rules .. priority-ordered, match or split

audit_log ...................... append-only, no foreign keys
```

A flag exists once per project. Whether it is on, and what it serves, is
per-environment. That split is what makes "promote this flag to production" a
representable operation, gives audit history and ownership something stable to
attach to, and keeps `type` from drifting between environments.

A flag with no `flag_environments` row in an environment is not rolled out
there, which is a different state from being disabled.

## Identifiers

Primary keys are UUIDv7, generated by the application — the schema has no
`DEFAULT`. Use `uuid.NewV7()` from `github.com/google/uuid`; do not fall back to
`uuid.New()`, which is v4. The time-ordered prefix matters most on `audit_log`,
the one append-heavy table, where random keys scatter inserts across the whole
B-tree instead of keeping them at its right-hand edge.

`projects.key` and `environments.key` are lowercase; `flags.key` and
`variants.key` permit mixed case, because developers write `checkoutV2` and the
flag key travels in the OFREP request path.

## version and revision

Two different counters, deliberately.

`flags.version` and `flag_environments.version` are optimistic concurrency
tokens, incremented by the `touch_row()` trigger on every `UPDATE`. Guard writes
with them and treat zero affected rows as a lost race:

```sql
UPDATE flag_environments
   SET enabled = $1
 WHERE id = $2 AND version = $3;
```

Without this, two concurrent kill-switch edits silently overwrite one another.
A `version` supplied by the caller is ignored; the trigger always wins.

`environments.revision` is a monotonic counter over *all* flag configuration in
that environment. It moves whenever a flag, flag_environment, variant or rule
belonging to the environment changes, via triggers calling
`bump_environments()`. It is the answer to three OFREP questions at once:

- what `ETag` a bulk evaluation response carries,
- whether an incoming `If-None-Match` can be answered `304 Not Modified`,
- when an in-memory evaluation snapshot is stale.

Every bump also emits `NOTIFY` on channel `itero_flag_config`:

```json
{ "environment_id": "0192...e001", "revision": 42 }
```

Nothing consumes this yet. It is here so the evaluation cache has an
invalidation signal to `LISTEN` for rather than a polling loop.

Bumping takes a row lock on the environment, so concurrent writes to the same
environment serialise. At management-API write volumes that is not a bottleneck,
and it is what makes the ordering meaningful.

## Flag types

`boolean`, `string`, `integer`, `float`, `object` — a `TEXT` column with a
`CHECK`, not a Postgres enum. `ALTER TYPE ... ADD VALUE` cannot run inside the
transaction golang-migrate wraps each migration in, which turns adding a type
into a multi-migration dance.

`integer` and `float` are separate because OpenFeature separates them and SDKs
expose separate typed getters. A single `number` type means a client calling the
integer getter on a value of `1.5` gets a client-side mismatch itero can neither
see nor prevent. `object` rather than `json` matches OFREP's own vocabulary.

A variant's JSON value must agree with its flag's declared type. This is
enforced as a `CHECK`, not a trigger: `flag_type` is denormalised from
`flags.type` down through `flag_environments` to `variants` by composite foreign
keys with `ON UPDATE CASCADE`, so the type is present in the row being checked
and cannot race a concurrent type change. `integer` additionally requires a
whole number.

A consequence worth knowing: changing `flags.type` cascades down, and the
variant `CHECK` rejects the cascade if any stored value no longer fits. You
cannot turn an `integer` flag into a `boolean` while integer variants exist.

`flag_type` on `flag_environments` and `variants` is filled by a `BEFORE INSERT`
trigger. Never write it.

## Targeting conditions

`targeting_rules.conditions` is a versioned JSONB document. The schema
guarantees only that `version` is a number and `clauses` is an array; everything
below is the parser's contract.

```json
{
  "version": 1,
  "op": "and",
  "clauses": [
    { "attribute": "tenant_id", "op": "eq",         "values": ["acme"] },
    { "attribute": "plan",      "op": "in",         "values": ["pro", "enterprise"] },
    { "attribute": "email",     "op": "ends_with",  "values": ["@acme.com"] }
  ]
}
```

- `version` — document schema version. Reject anything the evaluator does not
  recognise rather than best-effort parsing it.
- `op` at the top level — `and` or `or`, defaulting to `and`. How the clauses
  combine.
- `clauses` — an empty array matches everything, which is how a catch-all rule
  is expressed.
- `attribute` — a key in the OpenFeature evaluation context. `targetingKey` is
  addressable by that name.
- `op` in a clause — one of `eq`, `neq`, `in`, `not_in`, `contains`,
  `not_contains`, `starts_with`, `ends_with`, `gt`, `gte`, `lt`, `lte`,
  `exists`, `not_exists`.
- `values` — always an array, even for single-value operators. `exists` and
  `not_exists` ignore it.

A missing attribute makes its clause false; it is not an error. Comparison is
type-sensitive: `gt` on a non-numeric attribute is false, not a parse failure.

`rule_type` maps to the OFREP reason the rule produces — `match` yields
`TARGETING_MATCH`, `split` yields `SPLIT`. A `match` rule names the variant it
serves; a `split` rule names none and distributes across the weighted variants.
Unmatched-rules-so-serve-the-default is neither: that is `STATIC`.

## Variant defaults and weights

At most one variant per `flag_environment` has `is_default`, enforced by a
partial unique index. This replaces the old `flags.default_variant_id` /
`variants.flag_id` foreign key cycle, which forced two-statement creation and an
entire extra migration to close the loop.

*At least* one default is deliberately not enforced. A flag_environment with no
default has no value to serve, which is exactly how OFREP's code-default
response is represented on the wire — a successful evaluation with no `value`
property, telling the provider to use the application's own default. Pair it
with reason `DISABLED` for a disabled flag.

`weight` is null when there is no percentage split. When set on any variant of a
flag_environment it must be set on all of them and sum to 100. That invariant
spans rows, so it is a `DEFERRABLE INITIALLY DEFERRED` constraint trigger
checked at commit: a transaction may delete three variants and insert four
without every intermediate state balancing.

## Caveats

**Deferrable constraints cannot arbitrate `ON CONFLICT`.**
`targeting_rules_unique_priority` is deferrable so rules can be renumbered
inside a transaction without a temporary out-of-range priority. The cost is
that this fails:

```
ERROR: ON CONFLICT does not support deferrable unique constraints as arbiters
```

Upsert rules with an explicit `UPDATE ... WHERE` / `INSERT` pair instead.

**Trigger-maintained columns.** `updated_at`, `version`, `revision`,
`flag_type` and `flag_environments.project_id` are all written by triggers.
Application `INSERT`s supply the business columns only; `UPDATE`s that set these
are silently overridden.

**Deleting a variant a rule serves fails.** The foreign key is `ON DELETE
RESTRICT`, because nulling `variant_id` on a `match` rule would violate its own
constraint. Delete or repoint the rules first.

## Audit log retention

`audit_log` is append-only and has no retention mechanism yet — the sweep below
is documented, not scheduled. Decide the window before Epic 6 ships, because the
table only grows.

```sql
DELETE FROM audit_log WHERE created_at < now() - INTERVAL '365 days';
```

`idx_audit_log_project_created` supports that scan. At the volume where the
delete itself becomes the problem, switch to monthly `RANGE` partitioning on
`created_at` and drop partitions instead — cheaper than a bulk delete, and it
avoids the bloat a large delete leaves behind.

`actor` stays null until Epic 7 introduces authentication. Every row written
before then is an unattributed change, which is the argument for reordering
those two epics rather than shipping a log full of nulls.

## Rebuilding locally

The migration set was rewritten in place, so an existing database will be at a
version number whose content no longer matches. Drop and recreate rather than
migrating:

```sh
dropdb itero && createdb itero
```
